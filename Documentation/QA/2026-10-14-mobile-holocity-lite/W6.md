## Native rendering verification

The initial asynchronous render loop was misleading: JavaScript submitted 60 frames/second while the iOS simulator's Apple Software Renderer accumulated native work and intermittently displayed blank surfaces. **Those earlier 60 fps measurements and blank screenshots are invalid.**

The final renderer:

1. Mounts GL only after positive layout and preserves its native view hierarchy (`collapsable=false`).
2. Uses layout dimensions for viewport/projection because Expo's `drawingBufferWidth/Height` are initial snapshots.
3. Restores Expo's default framebuffer before each draw.
4. Waits for native completion with `gl.finish()`, `endFrameEXP()` and `flushEXP()` on every frame. Web skips the native-only barriers.
5. Cancels the render loop, frees GPU resources and explicitly destroys native contexts on disposal.
6. Uses a logical-pixel 3D surface, one sample and textured Lambert lighting by default. HUD/backdrop remain at normal display resolution. `renderScale` and `materialQuality="pbr"` are available for quality comparisons. Balanced lighting preserves base/emissive textures and opacity but omits PBR reflection/normal/ORM shading.

Three consecutive HARE → ACE → WOLF navigation cycles produced **9/9 visibly rendered screenshots**, without diagnostic GL snapshots or fallback images. The last cycle at 370×520 backing pixels showed:

| Bot | Context-to-first-draw | Completed native fps | GLB MB |
| --- | ---: | ---: | ---: |
| HARE | 1,216 ms | 8.9 | 1.681 |
| ACE | 984 ms | 10.1 | 0.989 |
| WOLF | 919 ms | 10.1 | 0.799 |

These are warm route loads with app assets cached, not cold app-start times. After six minutes and repeated navigation, the simulator app used approximately **100.7% CPU** (about one host core) and **193,600 KiB RSS**, compared with the earlier runaway queue's >900% CPU. This is a point sample, not a long-term leak profile.

A controlled HARE comparison improved from approximately **3 fps** at 555×780 full PBR to **6.6 fps** with balanced lighting, then **9 fps** at 370×520. Simulator software-renderer results do not establish physical-device performance. Root's final captured fleet/duel table supersedes these diagnostic-route samples.

Both final-guard ACE/WOLF duel measurements completed all three recorded rounds (9,600 ms timeline) with the same 402×832 native surface and combined **1,787,952-byte** bot assets:

| Run condition | First native draw | Active playback fps | Median |

| Later warm route, after Home/Detail and paused-round captures | 2,009 ms | 3.0–3.9 | 3.2 |
| App terminated, then opened directly to Duel | 2,632 ms | 6.9–8.2 | 7.65 |

Each row includes all four positive active-playback samples. The direct-launch control retained app asset caches; its load number is context-to-first-draw, not total app startup. [Warm-route raw evidence](evidence/duel-native-performance.json) and [direct-launch raw evidence](evidence/duel-cold-control.json) preserve both conditions. The difference remains unresolved. Log review found no concurrent Detail renderer: its final metric at line 12482 preceded the first Duel context at line 12483/12484, with no Detail metrics afterward. Subsequent duel contexts stopped emitting sequentially. No runtime changes were made between these two measurements. Both runs supersede the pre-guard duel sample; the observed active range is **3.0–8.2 fps**.

[Round 1](screenshots/DuelRound1.png), [round 2](screenshots/DuelRound2.png), and [round 3](screenshots/DuelRound3.png) show the final guard-loaded Skybreaker / LowRoundhouse / MeteorHammer takes and recorded HP/stamina snapshots. All three screenshots and the recorded result were visually checked.

The fresh-launch captures include the final animation lifecycle guard, which prevents a previously faded-out take's `finished` event from interrupting the currently requested receipt take. It does not change rendering settings or the measured asset workload.

`loadMs` covers GL context callback, cached asset reads, JS Meshopt decode, textures, rig setup, first draw and native finish/queue barrier. It excludes time before context creation and display-compositor presentation latency. `fps` counts completed native batches per two-second active interval; the first samples may include UI warmup. Logs/callbacks include backing dimensions, material quality, render scale and context ID. Diagnostic console logging is development-only.

- Native iPhone 17 Pro simulator on iOS 26.5: repeated cold/route rendering checks plus the 9-capture stability run above. Root records final fleet, roster/detail and three-round duel screenshots.
- Alias and actual-GLB HARE geometry tests cover the clip mappings and locomotion fix. TypeScript passes. Root's final validation report records the full-suite result.
- Source rigs do not contain derived hit, victory/defeat or guard takes. The documented recoil/shield fallbacks are presentation only.
- The deployed `rivalBattleHost` issue/settle shapes contain no round trace. Real client action history is labelled separately; missing traces remain result-only. The three-round ACE/WOLF preview is explicitly synthetic and grants no rewards.
- No W6 asset work is held. Physical-device fps and live authenticated host flow are not claimed by these simulator-only measurements.
